# 元数据启动校验与恢复边界（2026-10-07）

本轮修复 `BufferPool::LoadMeta` 将 magic 不匹配视为新库、跳过原页校验后改写的问题。
已有页在进入可写帧前检查原始 CRC、页号与 LSN 副本、物理页号 0、Meta 类型、
层级 1、tree_id 0、magic 和版本。L0 新增物理文件长度查询，防止短读补零掩盖截断。

只有物理空文件且无 WAL 记录、无历史检查点标记可以首次初始化。即使日志只剩
512 字节有效头，旧检查点标记也会阻止建库。初始建树事务被恢复回滚后，允许
从空元数据壳重新建库，但必须在有效 WAL 前缀中找到同页号、同 LSN 的完整 CLR，
按恢复规则盖 LSN 和 CRC 后与原始整页逐字节一致；非零 LSN 本身不能充当证明。

恢复仍先于加载：非正常退出且有效 WAL 有可重放页镜像时，可由原恢复流程修复。
干净关闭后的损坏，以及检查点已回收相关镜像的损坏，明确拒绝打开，保留数据文件。
本轮没有增加任意损坏恢复能力，也没有改变 WAL 格式、并发锁或页大小。

## 复跑

先分别构建 `build-ninja`、开启 ASAN 的 `build-asan` 和开启故障注入的 `build-fi`，
然后在项目根目录运行：

```powershell
python report/metadata/accept_metadata.py --output-dir report/metadata/my_run
```

输出目录必须不存在；验收入口不编译，记录实际二进制、源码哈希和构建缓存。
普通与 ASAN 的 ctest 可同时执行，各自子进程 cwd 为对应构建目录，测试文件互不共享。
元数据探针、结构守门和链路按顺序执行；测试耗时采用 ctest 自述的 real time，
并发运行的门槛测试用于正确性验证，不用于性能对照。
入口检查普通全量 ctest、两个结构守门、元数据专项、Python 协议、分层和 ASCII，
再跑两条独立正常链路及损坏元数据副本拒绝测试，最后复用原 78 项故障注入矩阵。
成功终点为 `METADATA_VERDICT: passed`，结果及耗时以 `acceptance_complete/manifest.json` 为准。
每项原始输出、数据库和故障现场保留在新目录中，历史恢复矩阵不被覆盖。

`acceptance/` 保留首轮验收：普通测试、守门及链路均通过，进入 ASAN 导入检查时
因裸工具名查找失败而终止；改为工具绝对路径后继续到 `acceptance_final/`。
中间目录的 `reused_normal_manifest.json` 和 manifest 明确记录普通证据的来源，
复用前核对所有生产源码与二进制哈希，未把首轮脚本失败记作完整验收通过。
复核发现检查点头边界后，中止 `acceptance_final/`（保留部分普通/ASAN 日志），
补测试和修复；`acceptance_complete/` 从新构建的最终源码重新跑全部门槛，不复用中间测试。
可用 `python report/metadata/verify_acceptance.py` 独立交叉核对原始日志、计数、
源码/二进制及保留数据；核对结果写入 `acceptance_complete/audit.json`。

首次回滚的 CLR 空壳由专项覆盖，实际强杀由既有矩阵覆盖。
本轮未重跑 30 分钟 C1 压测，未改变查询/迁移/页闩锁实现。
这组证据不替代 TSAN，也不将整个 M6/M7 标为完成；下一项是固定操作流混合读写基准。
