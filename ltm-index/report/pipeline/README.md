# 可复跑的完整主链路（2026-10-07）

续修：已加固已有元数据页加载，损坏页会在修改前被拒绝，合法恢复空壳要求精确 CLR 证明。
当前版本的链路、元数据负向测试和完整回归证据见 [元数据验收](../metadata/README.md)。
下文 `acceptance_validated/` 对应修复前入口版本，保留历史结果与缺口观测。

在项目根目录运行：

```powershell
python scripts/run_pipeline.py
```

入口自动构建 `ltm_pipeline`，创建独立输出目录，写入 512 条二维记录并保存
检查点，核对查询后关闭。随后启动另一个进程，打开同一份页文件和 WAL，
再次逐条核对记录和所有查询，生成报告。成功终点为 `PIPELINE_VERDICT: passed`；
错误状态、结果不符、缺少结构化结果、超时或源码变化均使整条链路退出 1。

每次运行默认新建带 UTC 时间戳的目录，也可指定尚不存在的目录：

```powershell
python scripts/run_pipeline.py --output-dir report/pipeline/my_run
```

保留 `database/pages.data`、`database/records.wal`、构建和两个进程的 stdout/stderr、
结果 JSON、构建缓存及 manifest。已有输出目录拒绝覆盖；`load` 阶段拒绝已有数据库，
`verify` 阶段要求已有文件，且没有 Put 或其他补写逻辑记录的路径。
`--skip-build` 用于复用已构建程序，报告会记录该参数；默认入口执行真实构建步骤。
ASAN 使用 `--build-dir build-asan`，须先构建开启 ASAN 的该目录；运行器配置运行库路径。

## 已发现的边界

这条链路证明正常检查点、干净关闭后的跨进程重开和查询一致性，不是新的强杀崩溃矩阵。
故意修改页 0 的 header.page_id 时，现有 `BufferPool::LoadMeta` 对已有元数据
使用 `FetchChecked(..., false)`，没有校验该页原来的 CRC/自描述，修改的字段仍
被保存而完整记录查询通过。该行为已实测记录为元数据页校验缺口，**不算恢复成功**；
见 `metadata_header_gap_observed.stdout.txt` 与 manifest 对应字段。
该缺口已在后续元数据专项修复，当前损坏副本应报错退出 1；历史观测不代表现有行为。
当前实现与恢复边界见 [元数据验收](../metadata/README.md)，下一项为混合读写基准。

`verified/` 和其余 `acceptance*` 目录保留开发过程证据：早期损坏用例错误地要求
修改元数据字段必然失败，或修改了页内无效碎片，另有验收脚本日志路径错误。
这些失败没有计入最终通过次数，最终以 `acceptance_validated/manifest.json` 为准。
